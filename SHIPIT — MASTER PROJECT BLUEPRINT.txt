# 1. PROJECT OVERVIEW

Project Name: ShipIt

Project Type: Mini Platform-as-a-Service (PaaS) / Push-to-Deploy Platform

Primary Goal: Build a lightweight, self-hosted deployment platform inspired by services such as Vercel, Render, and Heroku.

ShipIt will allow developers to connect a GitHub repository, trigger a deployment, build a Docker image, run the application in a container, and access the deployed application through a URL.

The platform should also provide deployment history, build logs, application health information, and intelligent deployment failure analysis.

ShipIt is being developed as a serious portfolio project to demonstrate practical Java backend engineering, Docker, infrastructure automation, deployment orchestration, security, and system design skills.

This is not intended to be another basic CRUD application.

The primary focus is to build a working deployment engine with a clean architecture and meaningful engineering decisions.

## Core Product Workflow

1. A developer registers and logs into ShipIt.
2. The developer connects their GitHub account.
3. The developer selects a GitHub repository.
4. ShipIt stores the project configuration.
5. A deployment is triggered manually or through a GitHub webhook.
6. ShipIt creates a deployment job.
7. The deployment worker clones the repository.
8. ShipIt detects the application type.
9. ShipIt builds a Docker image.
10. ShipIt starts the application inside a Docker container.
11. ShipIt performs a health check.
12. The deployment status is updated.
13. The developer can inspect deployment logs and history.
14. The deployed application becomes accessible through its assigned URL.

Additional capabilities will include:

- Live deployment logs.
- Deployment history.
- Rollback to previous successful deployments.
- Application health monitoring.
- Deployment failure analysis.
- Resource monitoring.
- Intelligent troubleshooting recommendations.

The platform will initially focus on Java/Spring Boot applications. Additional application types can be introduced later.

# 2. DEVELOPMENT PHILOSOPHY

ShipIt must be developed incrementally.

We will not attempt to build the entire platform in one prompt or one implementation session.

The development process will follow this workflow:

PLAN → REVIEW → APPROVE → IMPLEMENT → TEST → REVIEW → COMMIT → NEXT BATCH

## Mandatory Batch-Based Development Rule

EVERY major feature MUST be divided into small, logical implementation batches.

For example, Authentication should not be implemented in one enormous operation. It should be divided into batches such as:

- Batch 1: User entity and repository.
- Batch 2: User registration.
- Batch 3: Login and JWT generation.
- Batch 4: Spring Security configuration.
- Batch 5: Authentication tests and integration.

The same approach must be applied to every other feature.

IMPORTANT:

We will build each feature step by step and in batches so that tokens are used efficiently.

This is a mandatory project rule, not an optional recommendation.

For every feature:

1. First inspect the existing implementation.
2. Understand the dependencies and current architecture.
3. Prepare a feature implementation plan.
4. Divide the feature into small, independent batches.
5. Explain what each batch will implement.
6. Identify the files likely to be created or modified.
7. Identify dependencies and expected tests.
8. Wait for explicit user approval.
9. Implement ONLY the currently approved batch.
10. Run relevant tests and build verification.
11. Report changed files, implementation details, test results, and any issues.
12. Stop and wait for the user's next instruction.

Do not automatically continue to another batch.

Do not implement multiple batches just because they belong to the same feature.

Do not regenerate existing files unnecessarily.

Do not repeatedly explain the entire architecture in every response.

Inspect only the files relevant to the current task.

Keep implementation reports concise and useful.

Avoid consuming tokens on unnecessary explanations, repeated code, speculative features, or premature implementation.

A feature is considered complete only when all its planned batches are implemented, integrated, tested, and meet their acceptance criteria.

ShipIt should initially use a modular monolith.

The backend should contain logically separated modules with clear responsibilities.

The application should not be split into multiple microservices.

The deployment engine should operate through a background job processing mechanism.

## Architectural Rules

1. Keep business logic outside controllers.
2. Use service classes for business operations.
3. Use repositories for database access.
4. Use DTOs for API request and response objects.
5. Do not expose JPA entities directly through APIs.
6. Use proper exception handling.
7. Keep modules loosely coupled.
8. Avoid circular dependencies.
9. Use transactions where required.
10. Make deployment operations asynchronous.
11. Keep Docker operations isolated behind dedicated interfaces/services.
12. Keep deployment intelligence separate from the deployment engine.
13. The platform must continue functioning even if the intelligence module is unavailable.
14. Avoid unnecessary abstractions and design patterns.

- Identify the deployment stage where failure occurred.
- Suggest possible causes.
- Recommend corrective actions.
- Display the evidence supporting each diagnosis.

Example:

Failure:
Spring Boot application failed to start.

Evidence:
Connection refused while connecting to PostgreSQL.

Possible cause:
The configured database host or port is unreachable.

Suggested action:
Verify database availability and datasource configuration.

The system must distinguish between:

- Confirmed facts from logs.
- Likely causes.
- Possible explanations.
- Suggested fixes.

Never invent log evidence.

Never claim a root cause is certain without sufficient evidence.

Later enhancements:

- CPU and memory trend analysis.
- Restart pattern detection.
- Release regression detection.
- Rollback recommendations.
- JVM and Actuator metrics analysis.
- Optional LLM-based explanation layer.

The intelligence module must be independent of the core deployment workflow.

A failure in ShipIt Intelligence must never prevent a deployment from being executed.

## 1. Initial Development Scope

This scope decision is about implementation priority. It does not mean that future modules should be deleted or removed from the architecture documentation.

## 2. Caching Strategy

Caching should be introduced when there is a practical use case, rather than adding caching technologies without a clear requirement.

### Initial approach
- Use Docker BuildKit layer caching in the build engine to reuse previously built image layers and reduce repeated build times.
- Consider Caffeine for lightweight, in-memory application caching when a concrete use case arises.
- Use Spring Cache abstraction if application-level caching is introduced.

### Redis
- Redis is deferred for now.
- Do not introduce Redis merely to make the architecture appear more advanced.
- Reconsider Redis in a future upgrade if ShipIt requires distributed caching, shared state across multiple instances, or other capabilities that justify it.

### Caching principles
Any cache introduced must have a clear purpose and an appropriate strategy for:
- TTL and expiration.
- Maximum cache size.
- Cache invalidation.
- Data consistency.
- Memory usage.

Do not unnecessarily cache frequently changing deployment statuses, deployment logs, environment variables, or secrets. PostgreSQL remains the source of truth for application data and deployment jobs.
